# PDF 读取 / OCR 技术选型记录（2026-11-03）

## 结论先行

| 候选 | 定位 | 结论 |
|---|---|---|
| **MinerU**（上海AI Lab） | 版面重建 + 表格/公式 → Markdown | **不接入**：需 torch + 1.2B VLM，官方建议 8–16GB 显存，CPU 单页 10–30s；本流程只需"标题栏小字 OCR + 正则"，用不上版面重建 |
| **Docling**（IBM） | 文档→结构化，CPU 可跑 | **不接入**：即使 CPU 可用，也要拉 torch + 版面模型（数百 MB），只为一个裁剪区 OCR 属过度工程 |
| **Marker**（Surya） | PDF→Markdown，吞吐好 | **不接入**：同上，且 GPL-3.0、依赖 GPU 才快 |
| **PaddleOCR / PP-StructureV3** | 中文 OCR 最强梯队 | **不接入**：paddle 运行时体积大，本机已有 onnxruntime 路线 |
| **RapidOCR 3.x（PP-OCRv6 模型）** | onnxruntime 轻量 OCR | **实测不切换**：本批 10/10 与现役 v4 打平（详见下） |
| **pypdfium2（PDFium 渲染）** | 页面渲染引擎 | **已接入**：修掉"MuPDF 把某些扫描页渲染成全白"的静默故障 |

## 为什么不需要"更强的 PDF 解析"

本流程从 PDF 里要的只有两样东西：

1. **标题栏固定区域的字段**（图号/炉号/规格/重量行/材质）——裁一个矩形做 OCR，再走正则 + 图号字典纠错；
2. **图纸重量行那一行尺寸**——同样是一个小裁剪区。

版面分析、阅读顺序、跨页表格合并、公式转 LaTeX 这些"文档解析"的核心能力，在这里都用不到。
**表格数据根本不来自 PDF**：热处理尺寸来自 DXF/EXB，料单/大纲来自其自身表格。所以换重型解析器，收益≈0，风险=全流程重写 + 环境从 200MB 变 3GB。

## 实测记录

### 1) MuPDF 渲染全白（已修）

某批第 1 页（整页扫描，内嵌 3307×4677 灰度 JPEG）：

| 方式 | 结果 |
|---|---|
| `page.get_pixmap()`（PyMuPDF） | **整页纯白**，OCR 0 个文本块，且不报错 |
| `fitz.Pixmap(图片字节)` 直接解码 | 正常 |
| PIL 解码 | 正常 |
| **PDFium（pypdfium2）渲染** | 正常，均值 247.5 |

修法：新增 `pdfrender.save_page()`——MuPDF 出白图时自动换 PDFium 重渲染；PDFium 不可用再退回"抽取嵌入扫描图 + PIL 裁剪"。
正常页两引擎**像素差 = 0**（同 dpi 下逐像素比对），所以对既有批次零影响。

`pdfrender.py` 已接入：`build_manifest.py`（图纸标题栏）、`read_qty.py`（制造大纲）、`read_liaodan.py`（料单）。
注意 PDFium 的 `set_rotation` 是**绝对值**，传 0 会覆盖 PDF 自带旋转（横版图会变竖版），因此 `rot=None` 表示沿用页面自带旋转。

### 2) RapidOCR v4 vs v6（不切换）

同一批 10 页图纸标题栏，用现役 `rapidocr_onnxruntime 1.4.4` 与 `rapidocr 3.10`（PP-OCRv6 det/rec small）各跑一遍：

| 指标 | v4（现役） | v6 |
|---|---|---|
| 图号+炉号双确认 | 10/10 | 10/10 |
| 标题栏识别字数 | 154–278 | 161–280（略多） |
| 制造大纲 p1 | "核也石化"（错） | "核电石化"（对） |
| 制造大纲 p2 | 13 个炉号 | 12 个炉号（少 1） |

净持平。切换要改 `ocr2.py` 的调用层 + 新模型文件（数十 MB）+ API 变更，收益不成比例，**保持 v4**。
若以后出现某类字体长期识别差，再单点试 v6。

### 3) 顺带修掉的隐患

`read_qty` 找"制造大纲"时按"第一个非图纸 PDF"取，批次目录里一旦有本工具生成的**汇总 PDF**，就会被当成大纲 OCR 76 页。
已改为排除 `汇总 / 锻件尺寸图 / _锻件图 / 旧稿 / 封面`。

### 4) 电子版 PDF 是否有"跳过 OCR"的捷径

抽查两批 139 页 + 10 页图纸：文字层长度全为 0（纯扫描件），个别页 5–16 字（印章/水印）。
→ 无捷径可走，OCR 仍是必经环节。

## 何时再考虑重型解析器

- 需要从**非固定版式**的扫描文档批量抽字段（如各家不同格式的材质证明书）；
- 有 GPU 且要处理成百上千页/天；
- 需要把图纸里的**表格区域**（明细栏、技术参数表）结构化。

届时优先 MinerU（中文/表格最强），其次 Docling（CPU 友好）；接入方式是**新增一路数据源**，不动现有 manifest 抽取层。
