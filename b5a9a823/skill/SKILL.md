# 锻件尺寸图批量生成 skill

给一批「料单 + 产品图纸PDF + 热处理工艺exb」，产出锻件尺寸图 PDF（合并为单个文件）+ 复核清单。

## 工作区与环境（2026-11-02 起）

- 项目工作区与批次数据目录由使用者自行安排：本 skill 在 `<项目工作区>\b5a9a823\skill\`，批次数据通常与工作区平级（`<批次根目录>\<批次目录>\`）。
- **必须用系统 Python 3.11 跑**：`"C:/Program Files/Python311/python.exe" -X utf8 <脚本>`（pymupdf/rapidocr 都装在那；默认 `python` 没有 pymupdf，会全部出图失败）。
- 余量档之外的新规则（用户 2026-11-02）：**圆棒加余量后直径 < 50 的，直径抬升到 50**（`MIN_SOLID_D`，已实现于 make_batch.py，抬升会写入生成清单"问题"列）。仅作用于加余量路径；图纸直给尺寸不抬。
- 锻重缺失兜底：规格齐全且按锻件尺寸推算上限 ≤1000kg 时按 ≤1T 档出图，清单标注"档位待确认"；推算超 1T 仍不出图。
- manifest 补数脚本 `patch_manifest_240102.py`（批B 专用，含依据注释），补完后该批 82/82 全正式稿。

## 数据源地图（重要，别再绕路）

### 质保号字母 = 月份

`F24C0090` → **C = 12月**；`F24B0001` → **B = 11月**；`A = 10月`。
即 `F<年2位><月字母><流水>`。找料单/大纲时先由质保号字母定位到月份目录。

### SAP 料单（Excel，权威、可直读，不要 OCR）

```
<公司共享盘>\\电子清单\
    <NN>年料单\<M>月\XL-<客户>-<YY><MM>-<序号><客户>.xls   ← 老格式, 用 xlrd
    尺寸清单\                                              ← 近期单
```

**⚠ 这是生产网络盘，只读。不得写入、改名、删除，也不要往本地复制后再"顺手改回去"。**
需要处理就先复制到本地临时目录，源文件不碰。

读法：`.xls` 用 `xlrd`，`.xlsx` 用 `openpyxl(data_only=True, read_only=True)`。

关键列（实测 `批DXX单位.xls`）：
`物料号 | 质保号 | 序号 | 产品代号 | 名称 | 标准规格 | 材质 | 单重 | 总重 | 数量 | 台次 | 单价 | … | 交货期 | … | 规格变更 | 新物料号`

- **「规格变更」列优先级高于「标准规格」** —— 它是客户后来改的（如 F24C0091 `Φ300*308` → `Φ310*308`），你截图里手写的就是这一列。
- SAP 料单**没有** 批次/加样/锻重 列。

### 制造大纲（含 批次/加样/锻造重量kg）

**只有扫描版 PDF，没有 Excel 版**（用户 2026-11-02 明确：不用找了，如果有会放进工作区）。不要再花时间去搜。

形态：`<批次目录>\批C XX单位 B-001~009.pdf` 这类，表头
`质保号|序号|合锻编号|图纸代号|名称|材料|直径|长度|…|交货规格|数量|批次|加样|锻造重量kg`

其"锻造重量kg"列：小件常只写重量（`11`、`13.5`），大件会写**完整锻件尺寸**（`φ900/φ350×800×8%=4000`）。

**扫描版表格 OCR 不可靠**（实测 129 件仅 14 件能定稿），所以这一列的值一律**列成待核表交人工确认**，不自动采用。若用户日后提供 Excel 版大纲，放进批次目录即可，`make_batch.py` 会优先读它。

### 热处理报告

`<批次目录>\热处理工艺\*.exb`（文件名含 6 位炉号）。两条通道（make_batch 自动选择）：

- **DXF 优先**：用户在 CAXA 用「DWG/DXF 批转换器 → 按目录转换」导出，DXF 放 `<批次目录>\DXF\` → `read_ht2.py` 解析，结果正式稿；方块件/合锻/取样表也自动提取。
- **无 DXF 时 EXB 直读**：`read_exb.py` 直接解析 exb（125/125 与 DXF 一致），结果**一律标待核稿**；方块件/合锻/取样表不自动生成，需手工补 CSV。
- EXB→DXF 的自动转换**不存在可自动化途径**（已穷尽 COM/命令行/键盘模拟/开源调研，勿再调查；细节见"EXB 直读"一节）。

## 核心业务规则（用户 2026-10-31 / 2026-11-02 两轮确认）

### 锻件尺寸的取值优先级（最重要）

| 优先级 | 来源 | 处理 |
|---|---|---|
| **1** | **产品图纸"重量行"直接写了尺寸**，如 `Ø900/ø350×800×8%=4000kg` | **原样照用，不加任何余量**。这就是准确的锻件尺寸 |
| 2 | 热处理报告的"产品规格/热处理尺寸"列 → 取**热处理尺寸**（斜杠右列，全批 339/339 对都是右列长度=左列+10） | **热处理尺寸 + 余量档，每个方向都加**（用户 2026-11-02 定稿；此前代码误取产品列、且实心棒直径漏用热处理值，均已修复） |
| 3 | 都没有 → 用成品尺寸 | 加余量，标**待核稿** |

第 1 条是用户强调的关键："如果重量这有尺寸，那就直接用，这就是准确的锻件尺寸，直接套用就可以。"
第 2 条口径（用户 2026-11-02）："热处理尺寸上加余量"——余量档是双边补加（≤1T=10mm、1~3T=15、>3T=20），直径、长度都各加这么多；圆棒仍有直径 ≥50 下限。方块件按热处理尺寸每向 +10（`BLOCK_ADD`）。

### 热处理报告里的两个尺寸

一张热处理报告表格里常有**两行**，含义不同：

```
人孔管嘴  Ø900×Ø430×395 /        ← 成品尺寸(与产品图纸一致)
取样件    加长400取样 Ø915×Ø420×800 ← 取样件, 长度被加长过
```

**取非取样那一行**作为产品本体的热处理尺寸。含"取样/加长"的行只作参考。

### 配对与范围

- **配对键 = 批次号（炉号）**。热处理工艺卡会集中放在一个文件夹（同一客户、同一批年份），**不是全都要用**，只取图纸/料单里出现过的批次。
- 一张图号可对应多个炉号 → 出图单位是「图号+炉号」。

### 余量档（仅在优先级 2/3 时用）

`≤1T → +10`，`1~3T → +15`，`>3T → +20`
- 作用于**双边**：外径 `+a/2`（变大），**内径 `−a/2`（变小）**，长度 `+a`
- 用户明确：**内径加余量就是减小**，因为余量留给加工，孔加完余量后锻件孔径要比热处理孔径小

### 示意图性质

锻件图是**示意图**，形状不必精确，可夸大壁厚（`wall_exaggerate`），但**标注数值必须真实**。

## 完整流程总结（2026-11-02 定稿，批A 实战检验）

一个新批次从零到交付的完整动作（不管有没有热处理 DXF 都走这条线）：

1. **看料**：批次目录里有什么——产品图纸 PDF（几页、图号段）、制造大纲 PDF、热处理工艺（exb 还是已导出的 DXF）。exb 是 OLE 复合文件，**解析不了**；没有 DXF 时整批走"图纸重量行直给"路线。
2. **建 manifest.csv**：先跑 `build_manifest.py` 自动 OCR；**每页人工目检**（渲染 PNG 用眼睛核对图号/炉号/规格/重量行/名称/材质/件号范围），不可靠的字段直接手改 manifest——5 页小批手写比修 OCR 正则快且稳。新图号系列（如 `F25A0001`）会让 `norm_draw`/`RE_DRAW` 失效，注意 `F+两位+字母+四位` 的新格式。
3. **制造大纲必须看红笔批注**：红笔"变更数量以此为准"很常见，最终数量**以图纸标题栏为准**；大纲"取样"列（如"加4件φ30×990收样"）是样坯尺寸的出处；红笔箭头把炉号指给各序号，用来核对配对。
4. **写 样件尺寸.csv**（若有取样）：炉号 → 形状/取样外径/取样长度/取样件数。样图 = 取样行尺寸 **+10**（余量档按样重取），图号加"样"，**重量行留空**（样重与取样行尺寸常对不上，不猜）。
5. **跑 `make_batch.py`**：优先级 1（重量行直给，照用）→ 2（热处理+余量）→ 3（成品+余量，待核稿）。
6. **逐张抽检**：渲染 PNG 目检图形、标注、信息行、标题栏、重量。
7. **合并交付**：`merge_pack.py` 合并成 `锻件尺寸图_汇总.pdf`（首页自动生成复核表），**复制一份到批次目录**，命名 `<批次>_锻件尺寸图_汇总.pdf`。

### 判型规则（2026-11-02 定稿）

| 形状 | 判定 | 画法 |
|---|---|---|
| tube 筒 | 规格带内径 `Øa/Øb×L` | 剖切矩形双壁 |
| solid 圆棒 | `ØD×L` 且 L ≥ 0.9D | 单矩形剖视图，长径比截断到 [1.2, 3.6] |
| **disc 圆饼** | `ØD×L` 且 **L < 0.9D**（如 Ø320×70 法兰毛坯） | **双视图：上俯视圆(Ø) + 下侧视矩形(带剖面线)**，`draw_disc` |
| block 方块 | 三个无 Ø 尺寸 `a×b×c` | 双视图：上俯视 a×b + 下主视 a×L |

### 合锻与取样（批A 新口径）

- **N合1**：重量行尾缀 `(5合1)` = 本图号 5 件毛坯合锻成 1 根棒，数量÷N = 棒数。锻件图**按合锻后的整棒出一张**（用户 2026-11-02 指示），规格文字带 `(5合1)` 后缀（如 `Ø60×360(5合1)`）。
- **取样件**：本体重量行有 `/样XXkg` 且与本体重量不同 → 另出一张"图号+样"。尺寸来源**按用户指定：大纲取样行尺寸+10**（如 φ30×990 → Ø45×1000，圆棒仍受 ≥50 下限约束 → Ø50×1000）。
- 同图号两版本（如 F25A0001 版本A / F25A0002 版本B、同件号同炉号）：是两个质保号，**各出一张**。
- 取样行尺寸与图纸样重对不上时（如 4×φ30×990≈30kg vs 样23kg），按用户拍板的口径出图，并把矛盾记进生成清单"问题"列，不自行取舍。

## EXB 直读（2026-11-02 逆向打通，不再必须转 DXF）

`read_exb.py` 可直接解析 CAXA .exb 拿到文本（+坐标），**不需要 CAXA、不需要转换**：

- exb = OLE 复合文档；图形库在 `*BlockStg/*Blk_*` 流，`[20字节头][zlib]`，解压后 256KB 记录区。
- 文字实体记录以 `53 44 49 b3`（"SDI\xb3"）开头：`[uint32 字节长][UTF-16LE 文本]`，长度按 4 字节补 NUL；
  字符串后有若干小 double（字高/字宽/行距），再往后是插入点 `[float64 x][float64 y]`（x 与 DXF 差 <2mm，锚点语义）。
- **表格尺寸文本在另一块**（如 Blk_14c），转义是 CAXA 库内格式：`%c`=Ø、`%x`=×、`%d`=°、`%p`=±（单百分号，不是 DXF 的 %%c），
  格式码 `\pxt32.5;` 由 `read_ht2.clean()` 剥除。
- **验收口径（2026-11-03 修正）**：125 组 exb+dxf **精确同名**对照，`extract_one` 结果（外径/内径/长度）一致 **125/125 (100%)**。
  之前的 88% 是两个假象叠加，均已修掉：
  ① `\pxt5;` 格式码没剥干净，残留 `xt5;` 前缀让斜杠对正则失配 → `parse()` 改为直接复用 `read_ht2.clean()`，
     保证 EXB 与 DXF 文本完全同构；② 对照脚本用 6 位炉号前缀配对，`300002-1`/`300002二次重热` 等被错配到别的 DXF
     → 改为按文件名精确同名配对。**方块件三尺寸现在也能从 EXB 取到**（与 DXF 一致）。
  另对全部 132 份 exb（含无 DXF 的孤立文件）做鲁棒性测试：解析成功 132/132，取到尺寸 131，异常 0；
  唯一取不到的是 `300003`（`195×160×160` 带小数的方块件，走 `read_ht_block` 路径，不影响）。
- **安全口径（不变）**：EXB 直读出的热处理尺寸**一律按待核稿出图**（make_batch 里 `exb_mode`）。
  虽然对照 100% 一致，验证集只覆盖批B 一批；业务底线是"尺寸错一个数字就是报废件"，保守标记不取消。
  注意：**图纸重量行直给件不依赖 EXB，仍为正式稿**（`spec_override` 在 `exb_mode` 判定前就返回）。
- `read_exb.run(exb目录, out_csv)` 输出与 `read_ht2.run` 同构的 ht_dims.csv。

**EXB→DXF 自动转换不可行（勿再调查）**：CAXA CAD 2024 无命令行转换、无 COM 自动化接口（`CaxaDraft.Document` 仅 OLE 嵌入，
Dispatch 报"不支持此接口"）、无独立转换器 exe、无脚本(.scr)回放；键盘模拟实测会被系统焦点保护拦下（键打到别的窗口，危险）。
批转换器仍是人工 2 分钟的事，或者干脆用 EXB 直读绕过。

**联网调研补充（2026-11-03，用户授权下载更多项目后）**：已检索 GitHub / CAXA 官方资料并读了 `phosugar/caxa-mcp` 的说明：
- 没有可靠的开源 EXB 解析器；官方只提供 GUI「DWG/DXF 批转换器」。
- `caxa-mcp` 方向相反（用 ezdxf **生成** DXF 再让 CAXA 打开绘图），不提供 EXB→DXF 批量转换；依赖 CAXA 2023 + GUI 窗口焦点，本机是 2024。
- **结论：不引入外部工具**。EXB 直读已 100% 覆盖热处理尺寸需求，转换这一步本身冗余；引入 GUI 自动化/MCP 会增加
  焦点、版本、图元丢失等不确定性，违背可靠性底线。若将来确实需要"实体 DXF 文件"给别的系统用，唯一稳妥路径仍是
  人工跑一次 CAXA 批转换器，或单独评估 `caxa-mcp` 的 `caxa_send_command` 思路（**不要接进主流水线**）。

## 工具（工作区\工具\）

- **一键跑批\一键跑批.bat**：把批次文件夹拖上去 → 自动 manifest(缺才 OCR) → 热处理尺寸(DXF优先/EXB直读) → 出图 →

## 热处理尺寸提取：已打通（2026-11-02 更新）

用户用 CAXA「DWG/DXF 批转换器」→「按目录转换」把 125 份 exb 一次导出为 DXF 后，`read_ht2.py` 可直接解析。**不再需要人工填表。**

### CAXA DXF 的三个坑

1. **Ø 写成 `%%C` 转义码**，不是 Unicode。不先解码，所有尺寸正则全部落空。
2. **MTEXT 带字面反斜杠格式码**（`\fnsimsun|b0|i0|c134|p49;`、`\pxt32.5;`、`\P`），ezdxf 自带的 `plain_text()` 不认，要自己剥。
3. **表格序号会伪装成直径**：`64×210×250` 是"第64项 + 实心棒Ø210×250"，不是 Ø211/64×250。**只有带 Ø 标记的数才是直径**，必须据此判型，不能靠数值大小猜。

### 判型规则

| 原文 | 判定 |
|---|---|
| `Ø900×Ø430×395` | 筒体 外径911 内径430 长397.1 |
| `Ø210×250` | 实心棒 |
| `64×210×250` | 实心棒（前导数字是表格序号，丢弃） |
| 含"取样"的行 | 取样件，长度被加长过，**优先取非取样行** |

小数必须保留（`397.1` 不能四舍五入成 `397`）。

### 基准 = 热处理尺寸（不是成品尺寸）

`make_batch.py` 里 `base` 的取值：有 `ht_dims.csv` 就用热处理尺寸，否则退回成品尺寸并标"待核稿"。**没取到热处理尺寸时绝不能标正式稿。** 缺规格或缺重量（定不了档）→ 直接判"不出图"，不猜。

## OCR 引擎：**用 RapidOCR，不要用 Tesseract**

同一张标题栏实测对比（`out/tb1.png`）：

| 字段 | Tesseract | RapidOCR |
|---|---|---|
| 图号 | `F94B0010` ❌ | `F24B0010` ✓ conf=1.00 |
| 规格 | `511X800`（外径错） | `011X800` → 解析出 **Ø11** ✓ |
| 炉号标签 | `#5` | `炉号` ✓ |
| 表头/签名 | 全丢 | `表头与签名字段` ✓ |

安装（**必须走国内源**，默认 PyPI 直连会卡死）：

```bash
pip install rapidocr-onnxruntime -i https://pypi.tuna.tsinghua.edu.cn/simple
```

`ocr2.py` 已封装：`ocr_blocks()` 返回带坐标+置信度的文本块，`parse_fields()` 直接抽图号/炉号/内外径/长度/材质/锻重，并保留 `规格conf` 供闸门判断。Tesseract 仅作兜底。

## 旧：Tesseract 的现实与对策

扫描件无文字层，必须 OCR。本机可用：`C:\Program Files\Tesseract-OCR\tesseract.exe` v5.4.0 + `chi_sim`（语言包从 MasterPDF Editor 复制，未联网下载）。

实测错误模式与对策：

| 现象 | 对策 |
|---|---|
| `Ø` 被读成 `2`/`5`/`3` | 结构定位（规格总在两个长代号之后），不靠符号本身 |
| 图号 `F24B0010` 读成 `F94B0010` | **字典约束**：图号全集来自图纸文件名范围 `F24B0001~0099`，后4位唯一匹配即纠正 |
| 长度与相邻字段粘连 `850`+`003` | 合理性裁剪（20–20000mm） |
| 料单扫描件倾斜 ~0.5° | 自动搜索校正角 |
| 表格线切格 | **放弃**。扫描倾斜+内线太淡，形态学检测不出竖线；改用整页 OCR + 锚点行解析 |

**原则：OCR 只出草稿值，凡"字典纠正/歧义/不在合法集/规格未识别"一律进复核清单，不静默采用。** 工程图纸错一个数字就是报废件。

## 出图单位与标题栏（2026-11-02 用户第三轮口径，最终）

- **一个质保号一张图**。同质保号多个批次/多页 → 合并为一张，炉号写成一段：连续（或缺失的中间炉号是本批已知炉号）用 `首～尾`，否则逐个 `～` 相连（`merge_lu`）。
- 同质保号内各页**长度不一致**时，取**最长件**为代表并在生成清单标注"同质保号多尺寸(…), 取最长"——绝不静默丢尺寸。
- **加样件**：图纸 OCR 写 `本体kg/样xxkg` 且两重不一致（`RE_SAMPLE_W`）→ 另出一张，图号=质保号+**"样"**，尺寸取自热处理报告取样行（`read_ht_sample.py` → `样件尺寸.csv`，按行取 `…=1件` 那格）。样件尺寸取不到就"不出图"，不推算。
- **方块件（长方体，用户 2026-11-02 定稿口径）**：热处理卡片里是 3 个尺寸（如 `110×320×450`）。**尺寸 = 卡片"热处理尺寸"列每向 +10**（`BLOCK_ADD=10`），与锻重档位无关。画法 `draw_block`：上下两视图（上=俯视 A×B，下=主视 A×L，左右对齐），不标公差（用户明确）。数据由 `read_ht_block.py` → `块件尺寸.csv` 提取，关键判定链：
  - 卡片列是 `产品/热处理` 两列（`110×320×450 / 120×330×460=31件`），斜杠右列即热处理尺寸；
  - 产品 = 斜杠左里能找到"+10 搭档"的那个（3合1 合锻件的单件尺寸会挑错，如 300004 应取合锻后 120×210×670）；
  - 同截面里件数最多的是本体，件数 1 且更长的是取样件；取样优先按卡片写的"加长N"（本体L+N）匹配；
  - 卡片只写取样件的（300005/300006），本体按"产品+10"推算并**标待核**；
  - 同炉号有"重热"卡时只用正式卡。
- **合锻棒料（用户 2026-11-02 定稿）**：同炉几件合锻成一根 → **只出一张棒料图**，质保号、炉号都用 `/` 写在同一张（如 `F24B0020/F24B0021`），尺寸用卡片热处理列的棒料行 + 余量档（圆棒规则不变，直径有 ≥50 下限）。成员件不再单独出图；不同炉号的同名质保号（非合锻批次）照常单独出图。数据由 `read_ht_coforge.py` → `合锻表.csv`：判定 = 产品尺寸里"长度 ≈ 另两件之和 + 切断量(1~20mm)"，先排除热处理版(+10)和取样件；方块件不走此规则（块件口径本身按合锻后尺寸）。合锻行的"与序号N合锻"没有单件重量 → 档位按同炉号伙伴件锻重取（`lu_w`）。
- **数量口径（重要）**：SAP 料单的"数量"是棒材根数(1~2)，不是件数；件数在制造大纲扫描件里（`read_qty.py` → `数量表.csv`）。
- 标题栏 6 列：`版本|填图|复核|批准|名称|材质`（序号/数量两列已删，用户 2026-11-02）。名称从图纸 OCR 取（`_name`，优先含"毛坯"，取不到写"锻件"）。
- 重跑前自动把旧 pdf/json 归档进 `_锻件图\_旧稿_xx\`，防止旧图混入合并件。
